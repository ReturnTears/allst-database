# 10 删除与基数治理

## 场景

写错一段时间的数据要删掉，但删除不能变成“清空 measurement”。series 数量要能看出来，tag 的取值膨胀也要能看出来。

## 删除

`DELETE` 必须同时满足两件事：

- 有时间范围，规则和明细查询一样，最长 7 天
- `deviceId`、`region`、`metricType` 至少有一个

语句带保留策略：

```sql
DELETE FROM "rp_raw_7d"."device_metric"
WHERE time >= '...' AND time < '...' AND "device_id" = 'dev-001'
```

不带保留策略时，删的是默认策略。写入如果指定了别的策略，就会出现“接口说删了，点还在”。

```bat
curl.exe -X DELETE "http://127.0.0.1:8091/api/influx/metrics?deviceId=dev-001&metricType=temperature&range=1h"
```

这个接口不提供 `DROP MEASUREMENT` 和 `DROP DATABASE`。清掉整个指标库要到服务器上做，并且先有备份。

删除是按 shard 里的点删，不是瞬间释放磁盘。磁盘要等后续压缩才降下来。

## 基数

```bat
curl.exe http://127.0.0.1:8091/api/influx/governance/cardinality
curl.exe "http://127.0.0.1:8091/api/influx/governance/tag-values?key=region&range=7d"
```

`key` 只允许 `device_id`、`region`、`metric_type`。`SHOW TAG VALUES` 默认只看最近 7 天，避免为了列取值去扫全部历史。

`SHOW SERIES CARDINALITY` 返回的是 series 数量。`deploy/docker-compose.yml` 把单库上限放在 100 万。数量持续上涨时，先查是哪个 tag 的取值在涨，而不是先把上限调大。

样例数据是 5 条 series：两台设备各有温度和湿度，一台设备有电压。压测会多出 `bench-001` 这一条。

## 生产环境要注意

- 删除和连续查询可能同时写一个时间桶。删原始点不会自动删掉已经生成的 `device_metric_1m`。需要的话对聚合 measurement 再做一次回填，用覆盖把旧桶写掉。
- `region` 的取值应该是稳定的一小撮。如果这个接口返回了几百个区域，说明有人把城市、门店或临时标记写进了 tag。
- 基数查询本身不便宜，不要放到每个请求的链路上。给运维一个低频接口就够了。
