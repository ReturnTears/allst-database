# 02 基本查询

## 场景

查一台设备的一种指标。明细查询必须带 `deviceId` 和 `metricType`。不带这两个条件时，一个 measurement 里的 series 会被一起扫出来。

最新值用 `last()`，不要把明细拉回应用再取最后一条。

## 时间参数

区间是左闭右开：`time >= start AND time < end`。

| 传参 | 含义 |
| --- | --- |
| `range=1h` | 从现在往前 1 小时。单位只允许 `s`、`m`、`h`、`d`、`w` |
| `start` 加 `end` | 绝对时间。不要和 `range` 一起传 |
| 带 `Z` 或数字偏移 | 绝对时间 |
| `2026-10-24 08:00:00` | 没有时区时按 Asia/Shanghai |
| `2026-10-24` | 上海时区这一天的 0 点，并且 end 是开区间 |

明细和删除最长 7 天，和原始数据保留期一致。

## 分页

`order` 默认 `desc`。`limit` 默认 100，最大 500。

InfluxQL 的 `OFFSET` 会把前面的点都读出来再丢掉，所以这里不用。翻页用 `cursor`：

- `desc` 时条件是 `time < cursor`
- `asc` 时条件是 `time > cursor`

响应里的 `nextCursor` 只在结果正好是一条 series、并且本页已满时返回。一台设备如果换过 `region`，同一个 `deviceId + metricType` 会变成两条 series，这时不会给 cursor，响应里的 `hint` 会要求补上 `region`。

## 代码

- `com.allst.boot.metric.MetricQueryService`
- `com.allst.boot.influx.sql.MetricStatements`
- `com.allst.boot.influx.common.TimeRanges`

`FROM` 写明保留策略：`"rp_raw_7d"."device_metric"`。不写的话，查的是默认策略，和写入策略可能不是同一个。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/influx/metrics` | 明细。参数 `deviceId`、`metricType`、`region`、`range` 或 `start/end`、`cursor`、`order`、`limit` |
| GET | `/api/influx/metrics/latest` | 每条 series 的最新值。至少要 `deviceId`，默认看最近 7 天 |

响应里的 `influxql` 是实际执行的语句，方便对照。

## 调用示例

```bat
curl.exe "http://127.0.0.1:8091/api/influx/metrics/latest?deviceId=dev-001"
curl.exe "http://127.0.0.1:8091/api/influx/metrics?deviceId=dev-001&metricType=temperature&region=cn-east&range=2h&limit=10"
```

把返回的 `nextCursor` 原样带回下一页：

```bat
curl.exe "http://127.0.0.1:8091/api/influx/metrics?deviceId=dev-001&metricType=temperature&region=cn-east&range=2h&limit=10&cursor=2026-10-24T02:00:00Z"
```

## 生产环境要注意

- 查询一定要带时间范围。没有时间条件时，协调节点会扫全部 shard。
- 页面上的趋势图走 [03-函数与运算](03-函数与运算.md)，不要把 7 天的明细拉回 JVM 再算平均值。
- 打开 `logging.level.com.allst.boot.influx=DEBUG` 可以在日志里看到语句。默认不打，避免把查询文本灌满磁盘。
