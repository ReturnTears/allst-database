# 05 性能调优

## 场景

写入慢和查询慢分开看。写入先看客户端是不是在一条一条同步写，查询先看有没有时间范围、series 是不是太多。服务端参数放在 `deploy/influxdb.conf` 和 `deploy/docker-compose.yml`，不要散落在业务代码里。

`GET /api/influx/tuning/profile` 返回当前客户端参数。InfluxDB 连不上时，这个接口仍然返回配置，`serverReachable` 为 false。

## 客户端

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `influx.batch.actions` | 2000 | 攒够多少点就刷一次 |
| `influx.batch.flush-interval-ms` | 200 | 没攒够时最多等多久 |
| `influx.batch.jitter-interval-ms` | 50 | 多实例错开刷盘，避免同一毫秒打满 |
| `influx.batch.buffer-limit` | 20000 | 失败重试缓冲。小于 `actions` 时等于关掉重试 |
| `influx.batch.precision` | `MILLISECONDS` | 和 `DevicePoints` 的时间单位一致 |
| `influx.gzip` | true | 压缩写入 body |
| `influx.consistency` | `ONE` | 单节点用 `ONE`。`ALL` 会等最慢的节点 |
| `influx.batch.drop-on-queue-exhaustion` | false | true 时队列满了直接丢点 |

同步接口不走这套缓冲，见 [01-基本写入](01-基本写入.md)。压测接口两种都测：

```bat
curl.exe -X POST "http://127.0.0.1:8091/api/influx/tuning/benchmark?mode=sync&points=1000"
curl.exe -X POST "http://127.0.0.1:8091/api/influx/tuning/benchmark?mode=async&points=1000"
```

最多 5000 个点，写到 `bench-001`。异步模式的耗时包含 `flush()`，所以这个数字是数据已经送到服务端的时间，不是“放进队列就返回”的时间。

清理：

```bat
curl.exe -X DELETE "http://127.0.0.1:8091/api/influx/metrics?deviceId=bench-001&metricType=benchmark&range=1h"
```

## 服务端

`deploy/docker-compose.yml` 已经打开这些项：

- `index-version=tsi1`：series 索引放磁盘。内存索引在 series 变多后容易把进程打满。
- `max-series-per-database=1000000`
- `max-values-per-tag=100000`
- `max-body-size=25000000`：一次写入 body 的上限，要大于客户端一个批次的体积。

`deploy/influxdb.conf` 里还有这些查询侧开关，合并进真实配置后再用：

- `query-timeout`：一条查询最多跑多久
- `log-queries-after`：慢查询打日志
- `max-select-series`、`max-select-buckets`：防止一个查询扫出过多 series 或桶
- `cache-max-memory-size`：写入缓存上限
- `[continuous_queries] run-interval`：连续查询的调度间隔

这份 conf 不是完整的官方默认文件。覆盖容器里的配置前，先把镜像原文件拷出来再改。

## 生产环境要注意

- 先看 [10-删除与基数治理](10-删除与基数治理.md) 里的 series 数量，再调缓存。基数没控制住时，加大内存只是把问题推迟。
- 查询超时和最大 series 数在协调节点上限制。应用层的 7 天窗口和 `SLIMIT 20` 是第二道限制。
- `log-level=FULL` 会把请求和响应都放进内存。排障完改回 `NONE`。
- 压测不要打到生产库的业务 measurement。这里把压测点和样例设备分开了。
