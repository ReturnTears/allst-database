# 09 数据模型规范

## 场景

一条点表示某个设备在某个时刻的一种指标。先定 measurement、tag 和 field，再写接口。事后把 field 改成 tag，等于换一条 series，历史不会跟着走。

## 约定

库名 `allst_iot`。

| 位置 | 名字 | 说明 |
| --- | --- | --- |
| measurement | `device_metric` | 原始点 |
| measurement | `device_metric_1m`、`device_metric_1h` | 降采样，应用不直接写 |
| tag | `device_id` | 设备。会用来过滤，允许较高基数，但不是追踪号 |
| tag | `region` | 区域，取值要少 |
| tag | `metric_type` | `temperature`、`humidity`、`voltage` 这类短名字 |
| field | `value` | 浮点 |
| field | `status` | 整数，0 到 32767，可空 |

tag 值只允许字母、数字和 `_ . : -`，最长 64。空字符串、空格和引号在写入前就被拒绝。

同一个 measurement 里可以放多种指标，是为了少建 measurement。代价是聚合必须带 `metric_type`。如果某一类指标的 tag 集合完全不同，再拆 measurement，不要继续往这三个 tag 上加。

## 什么不能做 tag

下面这些值几乎每条点都不同，做 tag 会让 series 数接近点数：

- 追踪号、请求号
- 订单号、用户号
- 原始报文、异常堆栈

它们要么不要进 InfluxDB，要么做 field。field 不能作为 `WHERE` 的主要过滤条件，过滤仍然靠 tag 和时间。

series 的键是 measurement + tag 组合 + 保留策略。同样的键和时间戳写两次，后一次覆盖前一次。`/seed` 靠这个特性在同一分钟内重复执行而不增加点数。

## 字段类型

第一次写入决定类型。`status=1i` 是整数，`status=1.0` 是浮点。后面的写入必须跟第一次一致，否则服务端拒绝这一批。

`DevicePoints` 对 `status` 使用 `long` 重载，避免装箱后走 `Number` 重载被写成浮点。导出再恢复时也按整数写回。

查看当前类型：

```bat
curl.exe http://127.0.0.1:8091/api/influx/schema/fields
```

开发库如果已经写错类型，删掉 measurement 再初始化。不要在生产上删 measurement。

## 生产环境要注意

- measurement 名字用业务域，不用表名直译，也不要把日期编进 measurement。时间维度由 InfluxDB 自己管。
- tag 的取值在写入前就收成枚举。接口这里用字符白名单，是为了压测设备 `bench-001` 和样例设备都能写。真正的业务可以再收成固定枚举。
- 一个点至少有一个 field。只有 tag 的点写不进去。
