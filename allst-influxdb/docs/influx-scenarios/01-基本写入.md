# 01 基本写入

## 场景

设备上报一条指标，接口返回时这条数据已经写进 InfluxDB。同一台设备、同一个指标、同一个时间戳再写一次，后一次覆盖前一次。这是 InfluxDB 的更新方式，没有单独的 update。

原始数据进 `allst_iot.rp_raw_7d.device_metric`。字段约定见 [09-数据模型规范](09-数据模型规范.md)。

## 同步和异步

| 方式 | 接口 | 什么时候返回 |
| --- | --- | --- |
| 同步 | `POST /api/influx/metrics`、`/batch`、`/seed` | `BatchPoints` 直接写到服务端，返回表示已经确认 |
| 异步 | `POST /api/influx/metrics/async` | 点进入客户端缓冲。等到 `influx.batch.flush-interval-ms`，或调用 `/flush` |

`influxdb-java` 打开 `enableBatch` 之后，`write(Point)` 只是放进队列。需要调用方确认的接口不能走这条路径，所以同步接口使用 `write(BatchPoints)`，这个方法在 2.24 里会立刻发 HTTP。

异步接口适合采集量高、允许几百毫秒延迟的上报。进程被 `kill -9` 时，缓冲里的点会丢。正常停机会走 `close()`，客户端会先刷盘。

## 代码

- `com.allst.boot.metric.MetricWriteService`
- `com.allst.boot.metric.DevicePoints`
- `com.allst.boot.metric.MetricRules`
- `com.allst.boot.influx.client.InfluxGateway`

单次批量最多 1000 个点。时间不能超前 5 分钟，也不能早于 7 天，否则会落在保留策略外面，写入成功但马上被删掉。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/influx/metrics` | 写一个点 |
| POST | `/api/influx/metrics/batch` | 写一批点，请求体是 `{"points":[...]}` |
| POST | `/api/influx/metrics/async` | 放进客户端缓冲 |
| POST | `/api/influx/metrics/flush` | 把缓冲刷到服务端 |
| POST | `/api/influx/metrics/seed` | 写最近 60 个整分钟、5 条 series、共 300 个点 |

`status` 可以不传。传入时按整数写入，line protocol 里是 `status=1i`。先写成浮点再改成整数会失败，字段类型在 measurement 上不能改。

## 调用示例

先初始化库，再写样例：

```bat
curl.exe -X POST http://127.0.0.1:8091/api/influx/schema/init
curl.exe -X POST http://127.0.0.1:8091/api/influx/metrics/seed
curl.exe -X POST http://127.0.0.1:8091/api/influx/metrics -H "Content-Type: application/json" -d "{\"deviceId\":\"dev-001\",\"region\":\"cn-east\",\"metricType\":\"temperature\",\"value\":26.5,\"status\":1}"
```

同一分钟内重复调用 `/seed` 会覆盖这 300 个点，不会越积越多。换一分钟再调用，会多出新的时间戳。

## 生产环境要注意

- 业务确认要用同步写。异步写要有失败日志，批量线程的异常在 `InfluxClientConfiguration` 里打出来。
- `buffer-limit` 要大于 `actions`，否则失败点不会进入重试缓冲。
- 不要为了“实时”在每条业务事务里同步写 InfluxDB。写失败不应该把订单事务一起回滚，采集链路单独重试。
- 时间用毫秒。`DevicePoints` 固定用 `TimeUnit.MILLISECONDS`。
