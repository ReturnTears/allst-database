# 04 连续查询

## 场景

Cassandra 没有 `CREATE CONTINUOUS QUERY`。业务里说的连续查询，在这里是三件不同的事：

| 需求 | 做法 | 接口 |
| --- | --- | --- |
| 一个分区的结果一页一页取完 | 驱动的 paging state | `GET /page` |
| 导出或回填时把整张表走完 | 不带分区键的分页，沿 token 环继续 | `GET /scan` |
| 每小时的最小、最大、合计 | 应用读完一个分区，按小时聚合后写入 `sensor_hourly` | `POST /rollup` |

CQL 不能 `GROUP BY` 一个时间函数，所以小时桶在 `HourlyRollup` 里按 `Asia/Shanghai` 截断。重复执行会覆盖小时表里的同一行，不会把平均值再平均一次。平均值用 `value_sum / sample_count` 在读的时候算。

## 分页状态

`pagingState` 是这一条预编译语句的游标，用 URL-safe Base64 放在查询参数里。下一页原样传回来。换了设备、日期或指标，旧游标作废。

服务端只用当前这一页，不会在一次 HTTP 请求里把后面的页自动取完。页大小默认 100，最大 200。

全表扫描必须带 `confirm=scan`。这是为了避免一个普通查询参数漏了分区键，就去扫全集群。

## 降采样

`/rollup` 按页读 `sensor_reading` 的一个设备日分区，最多 5000 行。超过会返回 `truncated=true`，小时表只包含读到的这些行。单分区被切成一天，就是为了让这个上限够用。

小时表保留 90 天，压缩策略同样是按天的 `TimeWindowCompactionStrategy`。

## 代码

- `com.allst.boot.continuous.ContinuousService`
- `com.allst.boot.continuous.HourlyRollup`
- `com.allst.boot.cassandra.common.PageTokens`

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/cassandra/continuous/page` | 分区内续查 |
| GET | `/api/cassandra/continuous/scan` | 全表续查，`confirm=scan` |
| POST | `/api/cassandra/continuous/rollup` | 把一天聚合成小时表 |
| GET | `/api/cassandra/continuous/hourly` | 读小时表 |

## 调用示例

```bat
curl.exe "http://127.0.0.1:8100/api/cassandra/continuous/page?deviceId=dev-001&day=2026-10-24&metricType=temperature&pageSize=50"
curl.exe -X POST "http://127.0.0.1:8100/api/cassandra/continuous/rollup?deviceId=dev-001&day=2026-10-24"
curl.exe "http://127.0.0.1:8100/api/cassandra/continuous/hourly?deviceId=dev-001&day=2026-10-24"
curl.exe "http://127.0.0.1:8100/api/cassandra/continuous/scan?confirm=scan&pageSize=50"
```

第一页响应里的 `pagingState` 填到下一次请求。没有这个字段，说明已经到头。

## 生产环境要注意

- 在线接口一次只查一个分区。全表扫描放在定时任务里，并且限速。
- 不要自己用 `token(device_id, day_bucket) > ?` 拼导出，除非同时处理“一个分区被页边界切开”的问题。分页状态已经把这件事交给驱动了。
- 降采样任务按设备加日桶调度，失败从这一个分区重跑。不要用计数器表存小时结果，计数器重跑会累加。
- 小时表和原始表都会过期。任务如果跑得比原始数据的 7 天 TTL 还晚，源数据已经没了。
