# 08 数据模型规范

## 场景

Cassandra 先定查询，再定表。这个模块的查询是：

- 一台设备某一天的某个指标，按时间倒序
- 一个区域某一天的某个指标
- 一个指标某一天有哪些设备，走物化视图
- 一台设备的小时汇总
- 一个 SKU 的库存
- 一台设备的档案和阈值

这些查询不在一张宽表里用过滤凑出来。`GET /api/cassandra/schema/model` 返回同一份说明，不连接数据库。`GET /api/cassandra/schema/columns` 连接后可以核对 `system_schema.columns` 里的 `kind`：`partition_key`、`clustering`、`regular`、`static`。

## 表

| 表 | 主键 | 给谁用 |
| --- | --- | --- |
| `sensor_reading` | `((device_id, day_bucket), metric_type, recorded_at, reading_id)` | 设备时间线 |
| `reading_by_region` | `((region, day_bucket), metric_type, recorded_at, device_id, reading_id)` | 区域时间线 |
| `sensor_hourly` | `((device_id, day_bucket), hour_bucket, metric_type)` | 小时汇总 |
| `reading_by_metric` | `((metric_type, day_bucket), recorded_at, device_id, reading_id)` | 物化视图 |
| `device_hit_counter` | `((device_id, day_bucket), metric_type)` | 计数器 |
| `sku_stock` | `sku_id` | 轻量事务 |
| `device_profile` | `device_id` | 集合 |

`day_bucket` 是 `date`，由 `Asia/Shanghai` 从 `recorded_at` 算出来。它把分区从“一台设备的全部历史”收成“一台设备的一天”。目标是一个分区不要超过大约十万行、一百兆。所有设备、所有时间放进一个分区，会把压力打到一台机器上。

`device_model` 是 `sensor_reading` 的 static 列。一个分区里的每一行看到的是同一个值，存储上只有一份。它不参与聚簇。更新它会影响整个分区的这一格，所以不要拿它存频繁变化的状态。

## 建表时写上的约束

原始表和区域表：

- `default_time_to_live = 604800`，7 天
- `gc_grace_seconds = 86400`
- `TimeWindowCompactionStrategy`，窗口 1 天
- 只缓存分区键，不缓存行。时间序列几乎不会重复读同一行

小时表 TTL 是 90 天。计数器表不设 TTL，也不能有普通列。库存和档案用 `LeveledCompactionStrategy`。

`region` 强制小写。`deviceId` 区分大小写，`Dev-001` 和 `dev-001` 是两个分区。

`IF NOT EXISTS` 不会修改已经建好的表。主键改了就得换表名或删掉 keyspace 重建，不能 `ALTER` 主键。

## 如果集群一直在，可以再包 Repository

下面这段不是本模块在跑的代码。本模块自己持有 `CqlSession`，是为了 Cassandra 还没起来时应用也能启动。集群固定存在时，Spring Data 可以这样标主键：

```java
@Table("sensor_reading")
public class SensorReading {
    @PrimaryKeyColumn(name = "device_id", ordinal = 0, type = PrimaryKeyType.PARTITIONED)
    private String deviceId;
    @PrimaryKeyColumn(name = "day_bucket", ordinal = 1, type = PrimaryKeyType.PARTITIONED)
    private LocalDate dayBucket;
    @PrimaryKeyColumn(name = "metric_type", ordinal = 0, type = PrimaryKeyType.CLUSTERED)
    private String metricType;
}
```

Repository 方法的参数顺序也要服从分区键和聚簇列。它不会让“按 region 查 sensor_reading”变成合法查询。

## 生产环境要注意

- 一种查询一张表。第二种访问路径用双写或物化视图。
- 不要用 Cassandra 当队列。队头删除会产生一条很长的墓碑带。
- 集合不要放进时序分区。档案在 `device_profile`。
- 客户端生成完整主键，写入才幂等。
- 分区键里不要放无界的用户输入，比如完整的邮箱加每一秒的时间戳，基数会把索引和缓存打散。日桶是有意收窄之后的结果。
