# 05 性能调优

## 场景

遥测写入要稳，而不是把客户端线程池开得很大。这个模块把驱动参数放在配置里，并用一个最多 100 行的同分区批量写入看协调节点确认要多久。`/profile` 不连接 Cassandra，`/runtime` 读取 `system.local`、`system.peers` 和一部分 `system_views.settings`。

## 参数

| 配置 | 默认 | 原因 |
| --- | --- | --- |
| `consistency` | `LOCAL_ONE` | 遥测先保证写入成功。要确认副本时再改 `LOCAL_QUORUM` |
| `timeout` | 5s | 和协调节点的单次请求超时 |
| `page-size` | 500 | 驱动默认页大小。业务接口自己再限制到 200 或 500 |
| `pool.local-size` | 2 | 驱动 4 的默认本地连接是 1，忙的时候请求会在这一条连接上排队 |
| `pool.remote-size` | 1 | 本机房优先。远程机房只是备用 |
| 投机执行 | 关闭 | 默认就是 `NoSpeculativeExecutionPolicy`。非幂等写入被多发一次就会写重 |
| 幂等 | 按语句设置 | 带齐主键的 `INSERT` 为 true。轻量事务和计数器为 false，驱动不会自动重试 |

清单也可以从 `GET /api/cassandra/tuning/profile` 读到，和 `TuningNotes` 是同一份。

时序表使用 `TimeWindowCompactionStrategy`，窗口是 1 天，和日桶对齐。过期的一天会在压缩时整窗处理，比通用的 `SizeTieredCompactionStrategy` 更适合只追加的时间序列。库存和设备档案是小表、会更新，用 `LeveledCompactionStrategy`。

`UNLOGGED BATCH` 只出现在同一个分区里，每批最多 50 行。跨分区的 logged batch 会让一台协调节点做完所有分区的协调，写入吞吐更差。

## 代码

- `com.allst.boot.tuning.TuningService`
- `com.allst.boot.tuning.TuningNotes`
- `com.allst.boot.cassandra.client.CqlGateway`

`/benchmark` 往设备 `bench-tuning`、区域 `bench` 写 N 行，计时后删掉这两个分区。N 默认 50，最大 100。它用来看一批写入的延迟，不是压测工具。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/cassandra/tuning/profile` | 客户端参数和清单 |
| GET | `/api/cassandra/tuning/runtime` | 本节点、其他节点、挑选过的配置 |
| POST | `/api/cassandra/tuning/benchmark` | 同分区小批量写入 |

## 调用示例

```bat
curl.exe http://127.0.0.1:8100/api/cassandra/tuning/profile
curl.exe http://127.0.0.1:8100/api/cassandra/tuning/runtime
curl.exe -X POST "http://127.0.0.1:8100/api/cassandra/tuning/benchmark?rows=50"
```

`/runtime` 里的 `data_center` 必须和 `cassandra.local-datacenter` 一致。不一致时驱动会拒绝使用这些节点，表现就是连不上。

## 生产环境要注意

- 副本数是 3 时，要确认已经落盘的写入用 `LOCAL_QUORUM`。`LOCAL_ONE` 在一个节点刚写完就宕机时会丢。
- 页不要一次取几千行。应用内存和协调节点都会被撑住。
- `tombstone_warn_threshold` 默认 1000，`tombstone_failure_threshold` 默认 100000。删除太多时读会先变慢，再直接失败。处理方式见 [11-删除与墓碑](11-删除与墓碑.md)。
- 不要为了吞吐把连接池调到几十。一个节点上的原生传输线程是有限的，连接多了只是在排队。
- 预编译语句让驱动缓存。业务代码不要每次拼接一条新的 CQL，否则缓存会膨胀。
