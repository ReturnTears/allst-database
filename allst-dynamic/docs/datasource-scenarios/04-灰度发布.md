# 灰度发布

同一套表结构放在稳定库和灰度库。请求决定读哪一边，用来对照灰度配置和稳定配置，而不是在一张表里用 if 区分版本。

## 数据源

| 键 | 库 | 含义 |
| --- | --- | --- |
| `releaseStable` | `dyn_stable` | 稳定版本 |
| `releaseGray` | `dyn_gray` | 灰度版本 |

表 `t_feature`：`feature_key`、`feature_value`、`version_tag`。种子数据把 `checkout.button` 写成两边不同的文案，调用方能看出来打到了哪边。

## 决策顺序

`GrayDecider` 按下面的顺序，命中就停：

1. 请求头 `X-Gray-Version: gray` 进灰度库，`stable` 进稳定库。显式头覆盖后面的规则。
2. 请求头 `X-User-Id` 在白名单里，进灰度库。
3. 灰度比例 `percent` 大于 0，且带了用户 id：`floorMod(userId.hashCode(), 100) < percent` 进灰度库。同一个用户每次都落在同一边。
4. 其它情况进稳定库。没有用户 id 时不做百分比切流，避免一个匿名请求每次换库。

比例和白名单来自 `allst.datasource.gray`。`PUT /scenario/gray/policy` 只改内存，重启后回到配置文件。生产环境应放到配置中心，并保证同一用户在一段时间内稳定。

## 代码

- `GrayPolicy`：`@ConfigurationProperties(prefix = "allst.datasource.gray")`
- `GrayDecider`：纯函数
- `FeatureService`：决定数据源后读取 `t_feature`
- `GrayController`：`/scenario/gray`

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/scenario/gray/seed` | 两边各写一条不同的按钮文案 |
| GET | `/scenario/gray/decide` | 只返回数据源键，不访问数据库 |
| GET | `/scenario/gray/config` | 按规则读取特性配置 |
| GET | `/scenario/gray/policy` | 当前比例和白名单 |
| PUT | `/scenario/gray/policy` | 修改比例和白名单，`percent` 取 0 到 100 |

```bat
curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/gray/seed
curl.exe http://127.0.0.1:8000/dynamic/scenario/gray/config
curl.exe http://127.0.0.1:8000/dynamic/scenario/gray/config -H "X-Gray-Version: gray"
curl.exe -X PUT http://127.0.0.1:8000/dynamic/scenario/gray/policy -H "Content-Type: application/json" -d "{\"percent\":0,\"allowUsers\":[\"gray-user\"]}"
curl.exe http://127.0.0.1:8000/dynamic/scenario/gray/config -H "X-User-Id: gray-user"
```

不带头时 `versionTag` 为 `stable`。`X-Gray-Version: gray` 时为 `gray`，文案是「立即购买-灰度」。

## 注意

1. 灰度库和稳定库的表结构保持一致。灰度只换数据或配置，不在这里做不兼容的 DDL。
2. 写接口如果也要进灰度库，用同一套决策，不要写的时候走稳定、读的时候走灰度。
3. `hashCode` 足够演示「同一用户稳定落在一边」。生产环境换成明确的哈希，并约定桶的数量不再改变。
