# 分库分表

订单按用户拆到 2 个库、每个库 2 张表。库用动态数据源切换，表用 MyBatis-Plus 动态表名替换。算法写死，扩容要迁数据。运行期调整槽位的做法见 [05-数据分片](05-数据分片.md)，那是另一类场景。

## 数据源和表

| 键 | 库 | 表 |
| --- | --- | --- |
| `orderShard0` | `dyn_order_0` | `t_order_0`、`t_order_1` |
| `orderShard1` | `dyn_order_1` | `t_order_0`、`t_order_1` |

实体上的逻辑表名是 `t_order`。`OrderTableConfiguration` 只在 `OrderTableContext` 有值时把 `t_order` 换成实际表，其它表（包括旧的 `city`）保持原名。

## 路由

```
dbIndex    = userId % 2
tableIndex = (userId / 2) % 2
```

| userId | 数据源 | 表 |
| --- | --- | --- |
| 0 | `orderShard0` | `t_order_0` |
| 1 | `orderShard1` | `t_order_0` |
| 2 | `orderShard0` | `t_order_1` |
| 3 | `orderShard1` | `t_order_1` |

查询必须带 `userId`。订单号和雪花 id 里没有分片键，不能靠它们找库。`GET /orders/scatter` 会把 4 个物理表都查一遍，只给管理端核对，线上按用户的查询不要走它。

## 代码

- `OrderShardRouter`：纯函数，不访问数据库
- `TradeOrderServiceImpl`：先算路由，再 `push` 数据源并设置表名，`finally` 里清掉
- `TradeOrderController`：`/scenario/sharding`

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/scenario/sharding/route?userId=` | 只返回库和表，不访问数据库 |
| POST | `/scenario/sharding/orders` | 按 userId 写入 |
| GET | `/scenario/sharding/orders?userId=` | 只查该用户所在的一张表 |
| GET | `/scenario/sharding/orders/scatter` | 四个物理表都查 |

```bat
curl.exe "http://127.0.0.1:8000/dynamic/scenario/sharding/route?userId=2"
curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/sharding/orders -H "Content-Type: application/json" -d "{\"userId\":2,\"orderNo\":\"ORD-2\",\"amount\":18.50}"
curl.exe "http://127.0.0.1:8000/dynamic/scenario/sharding/orders?userId=2"
```

`userId` 为 2 时，响应里的 `dataSource` 是 `orderShard0`，`table` 是 `t_order_1`，`database` 指向 `dyn_order_0`。

## 注意

1. 表名上下文是 `ThreadLocal`。忘记 `clear` 会让后面的请求把 `city` 以外的 `t_order` 改写到错误的表。请求结束还有一道清理过滤器，业务代码仍然要在 `finally` 里清。
2. 分片键不要用会变的字段。用户换部门不应该导致订单换库。
3. 这个实现是应用内路由，方便和动态数据源放在一起看。数据量大、要透明分片时用仓库里的 `allst-sharding-proxy`，不要再套一层 dynamic-datasource。
