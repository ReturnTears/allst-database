# 主从粘滞与多数据源事务

这两个能力横跨前面的场景，单独记下来，避免写进读写分离或租户文档之后不好找。

## 主从粘滞

主从有延迟。一次请求里刚刚写完主库，后面的读如果去从库，会读不到自己写的数据。

`@WriteRoute` 在压入 `rwMaster` 之前调用 `ForceMasterContext.mark()`。同一请求里随后的 `@ReadRoute` 看到标记，就继续用 `rwMaster`，不再轮询从库。请求结束时 `RequestRouteCleanupFilter` 清掉标记，下一个请求恢复读从库。

也可以不写，直接在读请求上加 `X-Force-Master: true`。适合「写成功后的详情页」这类跨请求、但又必须读到最新数据的调用。调用方要知道自己为什么强制读主库，不要把所有读都加上这个头。

```bat
curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/rw/articles/read-after-write -H "Content-Type: application/json" -d "{\"title\":\"刚写的\",\"author\":\"ada\"}"
curl.exe http://127.0.0.1:8000/dynamic/scenario/rw/articles -H "X-Force-Master: true"
```

`read-after-write` 的响应里，`written.dataSource` 和 `read.dataSource` 都是 `rwMaster`。这是 Controller 分别调用两个 Service 方法，两次都走代理，标记才能留下来。如果在 `ArticleServiceImpl` 里用 `this.list()` 调用，切面不会执行。

## 多数据源事务

`@DSTransactional` 为本次调用里用到的每个数据源保留一条本地连接，方法正常结束一起提交，抛出 `Exception` 一起回滚。dynamic-datasource 3.5.1 的这个注解没有 `rollbackFor` 属性，只要是 `Exception` 就回滚。

它不是 XA。两个库没有统一的事务协调者。提交阶段如果后一个库失败，前一个库可能已经提交。演示和内部记账可以用，资金、库存这类不能接受单边成功的操作要换真正的分布式事务，或者改成同一库内的本地事务加可靠消息。

示例是租户转账：借方记在转出租户的库，贷方记在转入租户的库。`LedgerWriter.append` 使用 `@DS("#key")`，并且是独立的 Bean。`TransferService.transfer` 上标注 `@DSTransactional`。

`failAfterDebit=true` 时，借方插入之后抛出 409。两条流水都不应该留下。

```bat
curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/tenant/transfer -H "Content-Type: application/json" -d "{\"fromTenant\":\"a\",\"toTenant\":\"b\",\"amount\":9.90,\"bizNo\":\"rollback-1\",\"failAfterDebit\":true}"
curl.exe http://127.0.0.1:8000/dynamic/scenario/tenant/ledgers -H "X-Tenant-Id: a"

curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/tenant/transfer -H "Content-Type: application/json" -d "{\"fromTenant\":\"a\",\"toTenant\":\"b\",\"amount\":9.90,\"bizNo\":\"ok-1\",\"failAfterDebit\":false}"
curl.exe http://127.0.0.1:8000/dynamic/scenario/tenant/ledgers -H "X-Tenant-Id: a"
curl.exe http://127.0.0.1:8000/dynamic/scenario/tenant/ledgers -H "X-Tenant-Id: b"
```

成功时租户 `a` 有一条 `DEBIT`，租户 `b` 有一条 `CREDIT`，`bizNo` 都是 `ok-1`。转出和转入不能是同一个租户。

连接在事务里被 `ConnectionProxy` 包住：业务代码里的 `commit`、`rollback`、`close` 会被忽略，等外层 `LocalTxUtil` 统一处理。所以不要在 `@DSTransactional` 方法里再开 Spring 的 `@Transactional` 去提交其中一个库。

## 运行时数据源

租户和数据分片都会调用 `RuntimeDataSourceService`：

- `DefaultDataSourceCreator.createDataSource` 创建连接池
- `DynamicRoutingDataSource.addDataSource` 注册
- `removeDataSource` 摘除并关闭池

`master`、`slave` 以及各个场景的内置键在 `DataSourceKeys` 里保护，不能被覆盖或删除。`GET /scenario/datasources` 能看到键和分组，不返回账号密码。
