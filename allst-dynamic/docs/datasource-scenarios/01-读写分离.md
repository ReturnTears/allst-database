# 读写分离

写进主库，读从从库组里轮询。用来把查询从主库挪走。从库的数据靠 MySQL 复制过来，应用不要对从库做业务写入。

## 数据源

| 键 | 库 | 作用 |
| --- | --- | --- |
| `rwMaster` | `dyn_rw_master` | 写入，以及需要读到最新数据时的读 |
| `rwSlave_1` | `dyn_rw_slave_1` | 从库 |
| `rwSlave_2` | `dyn_rw_slave_2` | 从库 |

`rwSlave_1`、`rwSlave_2` 的第一个下划线之前是组名 `rwSlave`。`application.yml` 里的 `strategy` 使用轮询 `LoadBalanceDynamicDataSourceStrategy`。不要把主库命名成 `rwSlave_0`，它会进同一个组。

表 `t_article` 在三个库里结构相同。

## 路由规则

`@WriteRoute` 固定压入 `rwMaster`，并给当前请求打上主库粘滞标记。`@ReadRoute` 在进入方法时调用从库组的 `determineDsKey()`，选定 `rwSlave_1` 或 `rwSlave_2` 之后整段方法都用这一台。

同一个方法里如果先查列表再 `SELECT DATABASE()`，而每次取连接都重新轮询，两条 SQL 会打到不同从库，返回的库名也对不上这次查询。所以选定动作放在方法入口，不放在每次 `getConnection`。

粘滞和 `X-Force-Master` 见 [06-主从粘滞与多数据源事务](06-主从粘滞与多数据源事务.md)。

## 代码

- `ReadWriteRouteAspect`：切面，顺序是 `HIGHEST_PRECEDENCE`
- `ArticleServiceImpl`：`@WriteRoute` 写文章，`@ReadRoute` 读文章
- `ArticleController`：`/scenario/rw`

种子接口会把同一份文章写入主库和两台从库，用来模拟复制已经追上。业务写入接口只写主库。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/scenario/rw/articles` | 只写主库 |
| GET | `/scenario/rw/articles` | 轮询从库 |
| GET | `/scenario/rw/articles/master` | 显式读主库 |
| POST | `/scenario/rw/articles/read-after-write` | 写完立刻读，应仍在主库 |
| POST | `/scenario/rw/seed` | 三个库写入相同的两篇文章 |

```bat
curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/rw/seed
curl.exe http://127.0.0.1:8000/dynamic/scenario/rw/articles
curl.exe -X POST http://127.0.0.1:8000/dynamic/scenario/rw/articles -H "Content-Type: application/json" -d "{\"title\":\"新文章\",\"author\":\"ada\"}"
curl.exe http://127.0.0.1:8000/dynamic/scenario/rw/articles/master
```

连续调用几次 GET，`dataSource` 会在 `rwSlave_1` 和 `rwSlave_2` 之间交替。刚 POST 的文章只在主库，从库要等复制。本地没有复制时，用 `/articles/master` 核对写入。

## 注意

1. 注解放在实现类的公开方法上。Controller 里连续调用 `articleService.create` 和 `articleService.list` 会走代理；Service 内部自己调自己不会。
2. 不要在从库上开写事务。事务一旦在从库拿到连接，后面的写也会留在从库。
3. 生产环境的从库由复制维护。`/seed` 只用于本机把三个库灌成一样，方便观察轮询。
